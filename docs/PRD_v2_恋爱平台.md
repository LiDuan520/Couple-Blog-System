## 1. 背景与目标

### 1.1 现状
v1 已交付一个"个人博客 + 三件套（auth / user / blog）"系统，能写博客、上传头像、登录注册。但：

- **数据是单人的**：博客属作者本人，没有"我们"
- **缺少时间仪式感**：没有恋爱日、纪念日、在一起 X 天这种情侣最在意的元素
- **博客是唯一载体**：图片、关键日期都只能塞进博客 markdown，没有"事件/相册"等独立概念
- **首页空**：Dashboard 只是导航卡片，没有情感内容

### 1.2 改造目标
把"我写博客"升级为"我们一起记录"：

| 维度 | v1 | v2 |
|---|---|---|
| 单位 | User | **Couple（两人实体）** |
| 核心载体 | Blog | **事件流**（博客 + 纪念日 + 相册） |
| 时间感 | 弱 | **强**（恋爱日/纪念日/倒计时/时间轴） |
| 首页 | 导航 | **情感仪表盘**（在一起 X 天、下一个纪念日 Y 天、近期事件） |
| 数据归属 | author_id | **couple_id** |

### 1.3 成功指标

| 指标 | 目标 |
|---|---|
| 双人绑定完成率 | 注册用户中 ≥ 40% 完成绑定 |
| 恋爱日设置率 | 完成绑定的用户中 ≥ 95% 设置恋爱日 |
| 7 日留存 | 绑定后 7 日内仍登录 ≥ 60% |
| 时间轴停留时长 | 平均 ≥ 30 秒/次 |

## 2. 目标用户与场景

### 2.1 目标用户

- **20-35 岁情侣/夫妻**（含异地）
- 想要一个**比朋友圈私密**、比聊天记录**结构化**、比照片墙**有时间感**的空间
- 双方都是数字原住民，会扫码/输邀请码

### 2.2 核心场景

| 场景 | 描述 | 情绪 |
|---|---|---|
| S1 · 绑定 | 情侣一方注册后生成邀请码，另一方输入绑定 | 仪式感 |
| S2 · 设定纪念日 | 绑定后选择"在一起日"，系统展示"今天在一起 X 天" | 温暖 |
| S3 · 浏览时间轴 | 想回忆过去，打开时间轴看 1 年/3 年/5 年的事件流 | 怀旧 |
| S4 · 添加纪念日 | 创建 100 天、520、生日、七夕等纪念日 | 期待 |
| S5 · 上传照片 | 旅行/节日上传照片到相册，自动出现在时间轴 | 分享 |
| S6 · 写博客 | 重要日子用 Markdown 写长文，配几张图 | 沉淀 |
| S7 · 共同编辑 | 双方都能上传/编辑同一 Couple 下的所有数据 | 协作 |

## 3. 核心概念升级

### 3.1 新增概念

| 概念 | 定义 | 关键属性 |
|---|---|---|
| **Couple** | 一对绑定用户组成的空间单元 | id, user_a_id, user_b_id, anniversary_date, created_at |
| **Anniversary** | 可循环的纪念日 | id, couple_id, title, date, type, is_recurring, color |
| **Event** | 时间轴上的一项（聚合根） | id, couple_id, type, occurred_at, payload |
| **Photo** | 相册/图片墙中的图片 | id, couple_id, url, taken_at, album_id |
| **Album** | 图片分组 | id, couple_id, name, cover_photo_id, created_at |

### 3.2 改造后的关系

```
User (1) ──┐
           ├──< Couple >──┬──< Anniversary
User (1) ──┘             ├──< Event (聚合: Blog/Anniversary/Photo)
                          ├──< Album >──< Photo
                          └──< Blog (继承 v1, 加 couple_id 索引)
```

### 3.3 关键不变量

1. **一个用户最多属于一个 Couple**（v2 范围内；v2.x 考虑历史多 Couple 切换）
2. **Couple 必有 user_a / user_b**（顺序按 `user.id` 数值大小确定：`min_id` 为 user_a，max_id 为 user_b；SQLAlchemy 层加 `CheckConstraint(user_a_id < user_b_id)` 防止插入反序）
3. **Couple 必有 anniversary_date**（绑定时必填，不允许空）
4. **Anniversary date ≤ 今天**（恋爱日只能往前；v2 不支持"未来恋爱日"）
5. **新创建的 Blog / Photo / Anniversary 必须 couple_id 非空**（v1 老数据 `couple_id=null`，保留可读但不会出现在 Couple 时间轴中）

## 4. 功能需求

### 4.1 双人绑定（邀请码）

#### 4.1.1 邀请码生成

- 已登录用户 A 在 `Dashboard → 绑定伴侣` 点击"生成邀请码"
- 系统生成 **8 位大写字母+数字** 邀请码，例：`K3P9X7QA`
- 有效期 **7 天**（可重新生成，旧码立即作废）
- 同一时间用户 A 只能有 **1 个有效邀请码**
- UI 展示：邀请码（大字）、二维码、复制按钮、过期时间

#### 4.1.2 邀请码接受

- 用户 B（已注册）在 `Dashboard → 绑定伴侣` 输入邀请码
- 提交时校验：
  - 邀请码存在
  - 未过期
  - 邀请人不是 B 自己
  - 邀请人/被邀请人都未绑定
- 通过后：
  - 立即创建 Couple 记录（user_a=邀请人，user_b=被邀请人）
  - 跳转到"设定恋爱日"页面（强制流程）
  - 邀请码标记为已使用
- 失败错误：
  - `INVITE_NOT_FOUND` / `INVITE_EXPIRED` / `INVITE_SELF` / `ALREADY_BOUND`

#### 4.1.3 绑定后行为

- A / B 双方 `user.couple_id` 字段回填
- 双方立即可访问 `/dashboard`（重定向到恋爱仪表盘）
- A / B 双方 `auth/me` 响应增加 `couple: { id, partner: {id, username, nickname, avatar} }`

#### 4.1.4 解绑 / 换绑（v2 范围外但需预留接口）

- v2 不实现解绑 UI，但后端预留 `DELETE /couples/me` 软删
- 软删后 `couple.is_active=false`，数据保留，UI 不再显示

#### 4.1.5 数据迁移

- 现有 v1 用户在第一次进入绑定流程时：
  - 已绑定的不动
  - 未绑定的 UI 提示"v1 数据将随你绑定后保留"

### 4.2 恋爱日 & 倒计时

#### 4.2.1 设定恋爱日

- 绑定成功后强制引导设置（必填，日期选择器）
- 选 `anniversary_date` 必须是 **≤ 今天** 的日期
- 一旦设定，**任何一方不可改**（v2 范围；v2.x 增加"协商修改"功能）
- 双方都会收到一次站内提示（v2 简化：直接展示在首页"我们在一起 X 天"）

#### 4.2.2 仪表盘展示

- **大数字卡片**：在一起 X 天（X=今天−anniversary_date）
- **关键里程碑标记**：100 天、200 天、365 天、500 天、730 天、1000 天、1500 天、2000 天、3000 天、5000 天
  - 当日/次日显示"🎉 今天是我们在一起 100 天！" 横幅
  - 已过的里程碑也保留在时间轴对应位置
- **里程碑完整列表**（统一以技术设计 §5.2 为准）：`[100, 200, 365, 500, 730, 1000, 1500, 2000, 3000, 5000]`
- **下一个重要日期倒计时**（最多展示 3 个）：
  - 下一个周年纪念日
  - 下一个自定义纪念日（Anniversary 表）
  - 下一个生日（如双方有生日字段；v2 不做但预留 schema）

#### 4.2.3 计算规则

- "X 天"按自然日计算（忽略时区，统一 UTC）
- 周年纪念日 = `anniversary_date + N 年`（N≥1 还未到）
- 倒计时 0 天 = 当天；负数 = 已过去

### 4.3 时间轴视图

#### 4.3.1 入口

- Dashboard 顶部"打开时间轴"按钮
- 路由：`/timeline`

#### 4.3.2 视图

**倒序时间轴**（默认）：
- 按 `occurred_at` 倒序排列
- 每月分一组，组头显示 `2026 年 8 月` + 该月事件数
- 每条事件卡片显示：
  - 左侧：相对日期（"3 天前"/"今天"/"上个月"）+ 图标（按 type）
  - 中间：标题 + 摘要（前 100 字）
  - 右侧：作者头像（如果事件记录了 created_by_user_id）
  - 标签：纪念日/博客/相册
  - 点击 → 跳详情

**正序时间轴**（切换）：
- 按 `occurred_at` 升序
- 用于"从相恋开始回顾"模式
- 顶部固定显示"我们在一起 X 天 @ 当前事件日期"

**年视图**（切换）：
- 每个年份一张大卡片，统计该年事件数
- 缩略图墙（最多 6 张图）
- 点击进月份视图（复用倒序时间轴但已过滤年份）

**月视图**（切换）：
- 该月所有事件铺开

#### 4.3.3 筛选

- 按类型：全部 / 纪念日 / 博客 / 相册
- 按作者：双方 / 仅我 / 仅 TA
- 按时间：全部 / 近 1 月 / 近 1 年 / 自定义范围

#### 4.3.4 性能

- 分页：每页 20 条，滚动到底自动加载
- 顶部 3 个里程碑/纪念日卡片**不参与分页**，永远显示
- 首次加载 200ms 内返回（已实现 Redis 60s 缓存，命中即返回）

### 4.4 纪念日/事件管理

#### 4.4.1 类型（Anniversary.type）

| type | 说明 | 是否每年循环 | 例子 |
|---|---|---|---|
| `ONCE` | 一次性事件 | ❌ | 第一次见面 |
| `ANNIVERSARY` | 周年 | ✅ | 100 天、1 周年 |
| `BIRTHDAY_USER_A` | A 生日 | ✅ | — |
| `BIRTHDAY_USER_B` | B 生日 | ✅ | — |
| `VALENTINE` | 情人节/520/七夕 | ✅ | 每年重复 |
| `CUSTOM` | 自定义 | 可选 | 周年纪念日 |

#### 4.4.2 CRUD

- 创建：`POST /anniversaries`
  - 字段：title, date, type, is_recurring(默认按 type), color(默认红/粉/紫/蓝), icon(emoji)
  - 必填：title, date, type
- 列表：`GET /anniversaries?type=...&upcoming=true`
- 更新：`PATCH /anniversaries/{id}`（双方均可编辑）
- 删除：`DELETE /anniversaries/{id}`（软删，标记 `is_deleted=true`；30 天后由 cron 任务真删，见技术设计 §11 软删回收）
- 同一 Couple 最多 50 个自定义纪念日（防滥用）
- 超限行为：`POST /anniversaries` 返回 HTTP 422 + 错误码 `ANNIVERSARY_LIMIT_REACHED`

#### 4.4.3 自动事件（系统生成，非用户创建）

- 完整列表：`[100, 200, 365, 500, 730, 1000, 1500, 2000, 3000, 5000]`（与技术设计 §5.2 一致）
- 绑定后第 7 天：自动创建"在一起 1 星期"纪念日（不显示在 UI，作为时间轴数据点）
- 这些系统事件由前端在请求时间轴时**实时计算**塞入结果，不入库

### 4.5 相册/图片墙

#### 4.5.1 模型

- **Album**：分组容器
  - 例："2024 京都之旅"、"日常碎片"
  - 字段：name, description, cover_photo_id, photo_count, created_at
- **Photo**：
  - 字段：url, taken_at, album_id, width, height, exif(可选)
  - 一张照片属于一个 Album（必填），但可以"同时显示在时间轴"

#### 4.5.2 CRUD

- 创建相册：`POST /albums` (name, description?)
- 上传照片：`POST /photos` (multipart, file, album_id, taken_at?)
  - 复用头像上传的存储逻辑（`static/photos/`）
  - 单张 ≤ 5MB
  - 格式：jpg/jpeg/png/webp/heic（heic 仅展示提示用户转码）
  - taken_at 字段：可选；未填则默认 `now()`
- 列出相册：`GET /albums` (按 photo_count desc)
- 相册详情：`GET /albums/{id}` 返回照片列表（瀑布流）
- 修改照片：`PATCH /photos/{id}`（可改 `album_id`、`taken_at`；`couple_id` 不可改）
- 修改相册：`PATCH /albums/{id}`（改 name / description / cover_photo_id）
- 删除相册：保留所有照片，将 `photos.album_id` 置为 `NULL`（照片变为"未分类"，仍可访问，仍出现在时间轴）；相册记录本身真删
- 删除照片：`DELETE /photos/{id}`（真删文件 + DB 行）

#### 4.5.3 相册图片墙

- 首页 `/albums` 默认展示
- 卡片：封面图 + 名称 + 照片数 + 创建日期
- 网格视图：每行 3-4 张图
- Lightbox：点击放大，左右切换
- 时间轴整合：照片默认 `occurred_at = taken_at`（如果没填就 created_at）

#### 4.5.4 与博客的关系

- 博客里通过 Markdown `![](url)` 引用的图片**不入相册**
- 博客是文字+图组合；相册是纯图
- 两者通过时间轴汇聚，但相册有独立的浏览入口

### 4.6 博客（继承 + 改造）

#### 4.6.1 继承 v1 行为

- Markdown 编辑器
- 标题/内容/标签/公开标志
- 列表/详情/创建/更新/软删除

#### 4.6.2 v2 改造点

- `author_id` 字段保留（标识创建者），但**所有权限基于 couple**
- 列表默认查 `couple_id=me` 的所有博客（不限 author）
- 详情：双方均可看（私密博客从"只有作者"改为"双方可看"）
- 软删除：双方均可发起
- 时间轴上显示博客 `created_at`（或用户填的 `event_date` 字段，v2 新增）

#### 4.6.3 不变项

- 标签系统
- 公开主页（`/blogs/public/{author_id}`）保留，但**仅 author_id 是自己时可见**（不再暴露"共享给 Couple 的私密博客"）

## 5. 用户旅程

### 5.1 首次情侣注册+绑定旅程

```
[用户 A 注册] → [自动登录] → [引导：生成邀请码]
                                 │
                                 ▼  （A 把邀请码发给 B）
                          [B 输入邀请码] → [创建 Couple] → [强制：选恋爱日]
                                                              │
                                                              ▼
                                                  [A 收到"绑定成功"提示]
                                                              │
                                                              ▼
                                                  [跳转恋爱仪表盘]
                                                  [展示"在一起 0 天"]
                                                  [空时间轴 + 引导提示]
```

### 5.2 日常使用旅程

```
[打开 App] → [首页] → ┬─ [看倒计时：还有 3 天是 TA 生日] → [选礼物]
                      ├─ [看时间轴：上周我们去了 X] → [点开相册回忆]
                      ├─ [+ 新增纪念日] → [创建"周年纪念日"]
                      └─ [写博客] → [保存] → [自动出现在时间轴]
```

### 5.3 跨设备旅程

- 一方在手机上传了照片，另一方在 PC 打开时间轴能立即看到（< 60s 缓存刷新）
- 一方删除了博客，另一方 60s 后看到消失

## 6. UI/UX 要求

### 6.1 设计语言

- **情感化**：暖色调（粉/红/橙/紫渐变），圆角 8-16px，卡片阴影柔和
- **仪式感**：里程碑/纪念日当天有特殊动画（撒花、放大数字）
- **克制**：默认不弹通知、不闪烁（避免把"私人空间"做成"营销 App"）

### 6.2 关键页面

| 页面 | 路径 | 核心元素 |
|---|---|---|
| 恋爱仪表盘 | `/dashboard` | 大数字在一起 X 天 / 下一个纪念日倒计时 / 最近 3 个事件 / 快捷操作 |
| 绑定伴侣 | `/bind` | 生成邀请码 / 输入邀请码切换 Tab |
| 时间轴 | `/timeline` | 顶部固定里程碑 / 倒序事件流 / 筛选条 / 视图切换 |
| 纪念日管理 | `/anniversaries` | 卡片网格 / 新建按钮 / 类型筛选 |
| 相册列表 | `/albums` | 卡片瀑布流 / 新建相册 |
| 相册详情 | `/albums/:id` | 网格 + Lightbox / 批量管理 |
| 博客列表 | `/blogs` | 继承 v1，新增"双方筛选" |

### 6.3 响应式

- 桌面优先（≥1024px）
- 平板/手机可读（≥360px），但功能裁剪（Lightbox 单图，无批量管理）
- 移动端时间轴用**单列**布局

### 6.4 无障碍

- 颜色对比度 WCAG AA
- 所有按钮键盘可达
- 倒计时有 ARIA live region 通知

## 7. 非功能需求

### 7.1 性能

| 场景 | 指标 |
|---|---|
| 仪表盘首屏 | ≤ 1.5s（命中缓存） |
| 时间轴 20 条 | ≤ 800ms（命中缓存） |
| 上传 5MB 照片 | ≤ 3s |
| 倒计时计算 | 客户端纯计算，< 10ms |

### 7.2 安全

- 邀请码生成：8 位大写字母+数字，去掉易混字符 `0/O/1/I/L`（实现见技术设计 §12.1 `_generate_invite_code`），不可枚举
- 所有 Couple 相关 API 校验"当前用户属于该 Couple"（中间件层）
- 照片/相册权限：基于 couple_id
- 软删的博客/纪念日不能通过 ID 枚举访问（返回 404 而非 403）

### 7.3 数据一致性

- 绑定是事务操作（PG transaction）：创建 Couple + 更新双方 user.couple_id 必须同时成功
- 邀请码原子性：使用 `SELECT ... FOR UPDATE` 行锁
- 软删采用 `is_deleted=true` 标记，列表查询默认过滤

### 7.4 兼容性

- v1 API 在 v2 仍可用（旧客户端不会立即升级）
- v1 blog 数据迁移：**不动老数据**（v1 老博客 `couple_id=null`），老用户未绑定时仍可读自己的博客；绑定后，新博客自动归属 Couple，老博客继续以 author_id 归属本人
- 前端 v1 路由保留 fallback

### 7.5 可观测

- 新增关键日志：邀请码生成/使用、绑定成功、纪念日 CRUD
- 新增指标：绑定转化率、纪念日创建数、照片上传数
- 关键失败：邀请码被刷、绑定冲突，必须告警
